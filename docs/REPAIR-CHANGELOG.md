## AJ. Payment failures, Payments Log type, international bank accounts

- **Subscription "The server ran into a problem" (root cause):** the payment row is created, then Stripe rejects/fails the Checkout Session call, so the row is marked FAILED and a 502 is returned. Failures now carry `code: PAYMENT_PROVIDER_ERROR` (friendly message in EN/NL), and the server log line `Stripe POST /checkout… -> status code param message` states Stripe's exact reason. `FRONTEND_URL` must be a full `https://…` URL when Stripe is configured (checked at startup; it is used for the return URL).
- **Payments Log "Type":** the label was derived from the shop's *current* plan, so every subscription payment of a shop showed the latest plan. `payments.description` is now stored when the payment is created (e.g. "LocalSpotter Workshop") and shown. Migration `20261027100000_payment_description`. Rows created before this migration keep the old fallback label.
- **Bank account:** a valid IBAN is stored as before. Accounts without an IBAN (e.g. India) are accepted when bank name, BIC/SWIFT and 2-letter country are given; anything that looks like an IBAN must have a correct checksum. Stored encrypted (AES-256-GCM); the admin CSV shows `account | BIC | bank | country`. Error codes `IBAN_INVALID`, `BANK_DETAILS_REQUIRED`, `BANK_DETAILS_INVALID` have specific messages. International payouts are manual transfers.
- **Shop hidden / "No products found":** by design a shop and its products are public only while the subscription is ACTIVE with a future period end. The plan becomes ACTIVE only after a verified Stripe payment (webhook); failed payments leave it "Not active yet".
- **Live Render log showed `Stripe POST /checkout -> 400 invalid_request_error`** (Stripe refused the Checkout Session parameters). Hardening: `FRONTEND_URL` is normalised (missing `https://`, quotes) instead of failing; if Stripe says iDEAL is unavailable on the account, the session is retried without `payment_method_types` so the dashboard's EUR methods are offered; the log line now names Stripe's `param` and message. New admin button **Payments → Check payment setup** (`GET /admin/payment-diagnostics`) runs a trial EUR 1 checkout (expired at once) and shows Stripe's exact reason; the same check is logged 5 s after server start.
- **Root cause confirmed (Render log, setup check):** `param=payment_method_types — no longer supported when creating a Checkout Session`. The parameter is no longer sent; the Stripe Dashboard (Settings → Payment methods) decides which methods (iDEAL, cards…) Checkout offers. The temporary iDEAL-unavailable retry was removed as unnecessary.
- **"This conflicts with existing data" when changing plan (409):** `createPaymentIntent` refused any subscription that had *ever* a PAID payment, but a shop has one subscription row reused across plan changes and renewals, so after paying Webshop no other plan could be paid. For subscriptions "already paid" now means the subscription is ACTIVE with a future end date, and an open checkout is only reused when it was created after the current plan selection. Orders and workshop bookings keep the original rule.

## AK. "The server ran into a problem" when creating a shop route

- **Root cause:** `ShopRoutesService.createRoute` ran a leftover `business.findUnique({ where: { id: undefined } })` for every business owner. Prisma rejects a unique lookup without a key, so every owner's "Create route" ended in a 500. The unit test mocked that call, so it never failed. The dead query is removed and a regression test makes the mock behave like Prisma.
- **Safety net for the whole API:** a global `PrismaExceptionFilter` maps caller-side database errors to proper answers (P2002 → 409, P2003 → 400, P2025 → 404) and logs everything else with the Prisma code and route (`P2021/P2022` = migrations missing, `VALIDATION` = invalid query), so a 500 now always names its cause in the server log. Nothing from the database reaches the client.
